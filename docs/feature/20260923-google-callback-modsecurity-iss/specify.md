# Specify — Callback do login Google bloqueado pelo ModSecurity (parâmetro `iss`)

## 1. Problema

O login via Google (`intent=login`, `GoogleAuthController::loginRedirect()`/`handleLoginCallback()` — feature recém-mergeada, backlog item 014 fechado no commit `bf3eecaf40`) falha em produção com **406 "Not Acceptable" gerado pelo Mod_Security**, o mesmo WAF do HostGator que já tinha bloqueado o fluxo de vínculo em `docs/feature/concluidas/202609/20260901-google-oauth-state-opaco/`.

- **Reprodução:** usuário abre a tela de login, clica em "Continuar com Google", consente no Google. O Google redireciona o browser para `https://expense-api.novemax.com.br/api/auth/google/callback?state=<token>&iss=https%3A%2F%2Faccounts.google.com&...` — a request nunca chega ao Laravel; a tela devolvida é o HTML padrão do Mod_Security ("Not Acceptable! An appropriate representation of the requested resource could not be found on this server. This error was generated by Mod_Security."). Reproduzido em produção em 2026-09-23 (print do usuário, e de novo nesta investigação batendo direto em `GET /api/auth/google/login` — query string completa em §2.5).
- **Esperado vs. atual:** esperado — `callback()` roda `handleLoginCallback()`, emite o JWT e redireciona para `{frontend}/login?google_code=<code>`. Atual — 406 do WAF antes de qualquer linha de `GoogleAuthController` executar.
- **Diferença do bug já corrigido:** o `state` observado na URL (40 chars alfanuméricos) já é o token opaco gerado por `Str::random(40)` em `loginRedirect()` ([`GoogleAuthController.php:30`](../../../backend/app/Http/Controllers/GoogleAuthController.php)) — a correção de `20260901-google-oauth-state-opaco` está no ar e funcionando, não é a causa desta vez. O elemento novo na query string é `iss=https%3A%2F%2Faccounts.google.com`, que o `state` opaco não elimina porque quem gera esse parâmetro é o próprio Google, não a nossa aplicação.

## 2. Achados confirmados

### 2.1 `iss` vem do Google independentemente do escopo pedido — testado e confirmado, hipótese de tirar `openid` está descartada

`Laravel\Socialite\Two\GoogleProvider` pede por padrão os escopos `['openid', 'profile', 'email']` ([`vendor/laravel/socialite/src/Two/GoogleProvider.php:25-29`](../../../backend/vendor/laravel/socialite/src/Two/GoogleProvider.php)), e nenhum ponto do código chama `->scopes(...)` para sobrescrever isso — `grep "->scopes(\|Socialite::" backend/app` só encontra as 4 chamadas em `GoogleAuthController.php` (linhas 36, 59, 105, 165), todas sem override de escopo. A hipótese inicial era que pedir `openid` torna o fluxo uma requisição OIDC e a RFC 9207 (OAuth 2.0 Authorization Server Issuer Identification) faria o Google devolver `iss` só por isso — **testado nesta investigação e descartado**: construindo manualmente a URL de autorização do Google (mesmo `client_id`/`redirect_uri` reais) com `scope=profile email` (sem `openid`), o Google devolveu `iss=https://accounts.google.com` e `scope=...+openid` do mesmo jeito, tanto com uma conta que já tinha consentido antes (`isacaguiar@gmail.com`) quanto com uma conta sem nenhum histórico com este client (`disfagiaapp@gmail.com`, `authuser=3`) — descartando também "consentimento anterior" como explicação alternativa. Ou seja: **não há como evitar `iss` ajustando o escopo pedido pela nossa aplicação** — o Google inclui `iss` (e reescreve o `scope` de volta com as URIs completas) incondicionalmente para este client, antes da request chegar em nós.

### 2.2 O host não expõe gerência do ModSecurity (achado já registrado, ainda válido)

`docs/feature/concluidas/202609/20260901-google-oauth-state-opaco/specify.md:19` já constatou que o cPanel da HostGator usado em produção não tem menu de gerência do ModSecurity (só SSH / IP Blocker / SSL / API Tokens / Hotlink) e que desligar via `.htaccess` (`SecRuleEngine Off`) enfraqueceria a defesa de toda a API — por isso aquela feature corrigiu o lado da aplicação (`state` opaco) em vez de mexer no WAF. Nada nesta investigação indica que isso tenha mudado.

### 2.3 A rota de callback é pública e compartilhada pelos dois intents

`GET /api/auth/google/callback` está fora do grupo `Route::middleware('jwt.auth')` ([`backend/routes/api.php:23`](../../../backend/routes/api.php)), e o mesmo método `callback()` despacha para `intent=login` ou `intent=link` ([`GoogleAuthController.php:72-94`](../../../backend/app/Http/Controllers/GoogleAuthController.php)) — qualquer mudança de escopo/comportamento do redirect do Socialite afeta os dois fluxos igualmente, não só o login.

### 2.4 Em aberto — regra exata do ModSecurity não confirmada

Não há acesso a log do Apache/ModSecurity nem ao painel de segurança do host nesta sessão; a hipótese de que as URLs codificadas na query string (detalhe em §2.5) casam com alguma regra do OWASP CRS é consistente com o padrão do bug já resolvido (blob cifrado com `+`/`/`/`=` também foi barrado), mas não foi confirmada por log real — nem qual regra específica dispara, nem se é o `iss`, o `scope`, ou a combinação/tamanho total da query string que aciona o bloqueio.

### 2.5 Query string completa capturada — três URLs codificadas, não só `iss`

Reproduzindo o fluxo (produção, 2026-09-23) a URL bloqueada foi:

```
https://expense-api.novemax.com.br/api/auth/google/callback?state=<40 chars>&iss=https%3A%2F%2Faccounts.google.com&code=<code>&scope=email+profile+https%3A%2F%2Fwww.googleapis.com%2Fauth%2Fuserinfo.profile+https%3A%2F%2Fwww.googleapis.com%2Fauth%2Fuserinfo.email+openid&authuser=0&prompt=consent
```

Além do `iss`, o parâmetro `scope` que o Google devolve contém **duas outras URLs codificadas** (`https://www.googleapis.com/auth/userinfo.profile` e `.../userinfo.email`) — o Google sempre expande `profile`/`email` pras URIs canônicas completas na resposta, independente da forma curta pedida. São três ocorrências de `https%3A%2F%2F...` na mesma query string, o que é um padrão ainda mais forte pra disparar uma regra genérica de "URL embutida em parâmetro" do OWASP CRS do que só o `iss` sozinho — reforça que a causa provável é esse padrão geral, não um parâmetro específico isolado (achado consistente com §2.4, ainda não confirmado por log).

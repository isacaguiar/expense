## Dados da conta

- **Conta de hospedagem:** `isacag00`
- **Caminho da aplicação:** `/home1/isacag00/novemax/expense/api/` (raiz do Laravel; docroot do subdomínio é `.../api/public`)

## Assunto sugerido

Bloqueio 406 (Mod_Security) em callback OAuth legítimo — preciso de exceção pontual, não desligar o WAF

## Descrição do problema

Minha aplicação (Laravel, hospedada em `expense-api.novemax.com.br`) usa "Login com Google" (OAuth 2.0). Depois que o usuário consente no Google, o próprio Google redireciona o navegador de volta para uma URL da minha API, e é **exatamente esse redirecionamento legítimo do Google que está sendo bloqueado pelo ModSecurity de vocês**, com a resposta:

```
Not Acceptable!
An appropriate representation of the requested resource could not be found
on this server. This error was generated by Mod_Security.
```

A requisição não chega nunca ao meu código PHP/Laravel — o bloqueio acontece antes, no nível do Apache/ModSecurity.

### Exemplo real de URL bloqueada (dados de teste, sem informação sensível de usuário)

```
https://expense-api.novemax.com.br/api/auth/google/callback?state=<state-40-caracteres>&iss=https%3A%2F%2Faccounts.google.com&code=<codigo-de-autorizacao>&scope=email+profile+https%3A%2F%2Fwww.googleapis.com%2Fauth%2Fuserinfo.profile+https%3A%2F%2Fwww.googleapis.com%2Fauth%2Fuserinfo.email+openid&authuser=0&prompt=consent
```

Reproduzido em produção em 2026-09-23, mais de uma vez, com contas Google diferentes.

### Por que acontece (nossa hipótese, sem acesso ao log do ModSecurity para confirmar)

A URL que o Google gera tem **três valores de parâmetro que são, eles próprios, URLs codificadas**:
- `iss=https%3A%2F%2Faccounts.google.com`
- dentro de `scope=`: `https%3A%2F%2Fwww.googleapis.com%2Fauth%2Fuserinfo.profile`
- e `https%3A%2F%2Fwww.googleapis.com%2Fauth%2Fuserinfo.email`

Isso é um padrão comum de disparar regras genéricas do OWASP Core Rule Set (CRS) que detectam "URL embutida em parâmetro" como possível ataque (SSRF/open redirect). No nosso caso é falso positivo: são parâmetros padrão que o próprio Google sempre inclui na resposta OAuth/OIDC — não temos como alterar o que o Google envia.

Já tivemos um bloqueio parecido antes (blob de `state` cifrado, também barrado pelo Mod_Security) e resolvemos do nosso lado trocando por um token opaco mais simples. **Desta vez não é possível resolver só do nosso lado**, porque quem gera os parâmetros problemáticos (`iss`, `scope`) é o Google, não a nossa aplicação.

## O que estou pedindo

**Não** quero desligar o ModSecurity pra todo o domínio — isso reduziria a proteção da API inteira. Pedidos, em ordem de preferência:

1. **Identificar a regra exata do ModSecurity/OWASP CRS que está barrando essas requisições** (a partir do log de erro do Apache do meu domínio, no horário dos testes citados acima) e criar uma **exceção pontual só para essa regra, só na rota** `GET /expense/api/public/api/auth/google/callback` (ou o path equivalente que vocês identificarem no log).
2. Se não for possível uma exceção só por regra+rota, um **`SecRuleRemoveById` (ou equivalente) escopado só a essa rota específica** via `.htaccess` ou configuração de vhost — mantendo o ModSecurity ativo para o resto do domínio.
3. Se nenhuma das opções acima for possível pelo suporte, preciso saber se existe algum jeito de eu mesmo consultar o log de erro do ModSecurity para essa conta (hoje o painel só mostra SSH / IP Blocker / SSL / API Tokens / Hotlink em Segurança, sem opção de gerência do ModSecurity).

Fico à disposição para fornecer mais exemplos de URL bloqueada, ou os horários exatos (fuso `America/Sao_Paulo`) das tentativas, se ajudar a localizar a entrada no log.

## Informação de contexto (se pedirem)

- Aplicação: Laravel 11 (PHP), backend de um app de controle de despesas.
- A rota afetada é pública por design (é o callback OAuth do "Login com Google"), então não está atrás de autenticação — isso é esperado e não é uma falha de configuração da minha parte.
